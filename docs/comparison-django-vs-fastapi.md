# Порівняльний аналіз Django (DRF) і FastAPI на матеріалі проєкту

| Аспект | Django + DRF (у проєкті) | FastAPI (у проєкті) |
|---|---|---|
| Призначення в системі | Основний застосунок: сайт, адмінка, ролі, CRUD, REST API | Окремий сервіс підбору: індекс навичок, метрики подібності, WebSocket |
| ORM | Django ORM: міграції з коробки, `select_related/prefetch_related`, адмін-панель | SQLAlchemy 2.0 async: більше коду, але повний контроль над запитами, `asyncpg` |
| Валідація | Serializer / ModelForm / `Model.clean()` + обмеження БД | Pydantic v2: типи → валідація → схема OpenAPI автоматично |
| Документація API | `drf-spectacular` (потребує налаштування) | Swagger/ReDoc автоматично з типів і `response_model` |
| Автентифікація | Сесії для вебу, SimpleJWT для API, групи/дозволи | `OAuth2PasswordBearer` + PyJWT, ролі у залежностях (`Depends`) |
| Конкурентність | Синхронний WSGI (gunicorn), фонові завдання — Celery | `async/await`, `WebSocket` і `BackgroundTasks` «з коробки» |
| Міграції | `makemigrations/migrate` — автоматично з моделей | Alembic: ревізії пишуться/перевіряються вручну |
| Тестування | `pytest-django`, `assertNumQueries`, тестовий клієнт | `TestClient`, `dependency_overrides` для підміни залежностей |

## Висновок
Django виправданий там, де потрібні **готові механізми**: адмін-панель, форми, ролі, міграції, шаблони — це 80 % функціональності
платформи рекрутингу. FastAPI виправданий для **вузького високонавантаженого сервісу** без UI: підбір відповідностей
(CPU/IO-легкий, багато однотипних запитів), WebSocket-сповіщення, чіткий контракт із типами. Розділення дає незалежне
масштабування й деплой, але додає вартість: міжсервісну автентифікацію, дублювання даних (індекс) і узгодженість «зрештою»
(eventual consistency) — Django не блокується на FastAPI, а індекс відновлюється повною переіндексацією.

*Навантажувальний тест (Locust) не проводився: файл `docs/locustfile.py` підготовлено, але результати не наведено.*
